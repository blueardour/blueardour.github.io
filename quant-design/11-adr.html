ADR 流程与 0001–0004 四个初始决策。

架构决策记录（ADR）

ADR 记录重要且难以逆转的决策及理由。它防止同一问题反复争论，也防止后续改动悄悄 偏离原设计。

何时必须写 ADR

  • 分层/依赖方向变化；
  • 单一真相源/所有权变化；
  • 核心契约变化（Intent/Order/Fill/AccountSnapshot/ExitPlan 等）；
  • 执行语义变化（成交、费用、T+1、涨跌停、部分成交）；
  • 配置 schema 变化；
  • 参考框架/新运行时依赖；
  • 会推翻已有预注册实验的变更。

纯文档修正、错别字、链接修复不需要 ADR。

生命周期

Proposed → Accepted → Superseded | Deprecated

  • 永不删除 ADR；被替代时保留原文，并在头部链接新 ADR。
  • 单用户项目允许自我批准，但必须记录日期和理由。
  • Accepted ADR 优先于 design_spec.md；design_spec.md 必须链接 ADR。

编号与命名

NNNN-short-kebab-title.md，四位递增。一个 ADR 只做一个决策。

索引

ADR 决策 状态

见 template.md。

变更流程

  1. 复制模板，编号，状态 Proposed。
  2. 写清 Context/Decision/Consequences/Alternatives/Verification。
  3. 更新 design_spec.md 对应章节并双向链接。
  4. 更新 roadmap.md 阶段/偏差。
  5. 改代码 + 测试；DoD 通过后置 Accepted。
  6. 若替代旧 ADR：旧文件头部加 Superseded by NNNN，新文件写 Supersedes NNNN。

0001: 以 NautilusTrader 作为概念参考

  • Status: Accepted
  • Date: 2026-11-04
  • Owner: architecture
  • Supersedes: none
  • Superseded by: none

Context

系统要从“研究脚本”演进到可回测、可 paper、可实盘、可视化的单用户 A 股/港股系统。 需要一套成熟的领域词汇和分层，避免继续在 backtest/engine.py 上叠加状态。候选框架：

  • NautilusTrader：事件驱动、回测/实盘同管线、Portfolio/Execution/Risk 分层清晰；
  • vn.py：国内实盘生态好，但架构较旧、全局状态多；
  • Backtrader：简单，但实盘/部分成交/订单类型弱；
  • Zipline/Qlib：研究/回测强，实盘弱。

Decision

以 NautilusTrader 作为唯一主要概念参考，但不引入其运行时依赖。

借用：

  • ports/adapters：数据、执行、broker 适配器；
  • Order/Fill 生命周期与显式状态；
  • 回测/paper/live 共用策略与执行管线；
  • 注入 Clock、只读账户快照；
  • Instrument 作为一等元数据（lot/tick/currency/price limit）。

不借：

  • actor/message bus/async 运行时；
  • 多 venue 路由、完整 instrument universe；
  • Nautilus 内部实现/打包/Rust/Cython。

A 股/港股规则（T+1、100 股整手、涨跌停、印花税、港股 board lot）由本项目 execution/ 和 datafeeder/ 显式建模，不能依赖框架。

Consequences

  • 正面：有成熟词汇和清晰边界；回测/实盘同管线；后续接券商只需实现 BrokerPort。
  • 负面：概念偏多，需要做减法；不能直接复制 Nautilus 的复杂 runtime。
  • 中性：vn.py 的券商 gateway 经验可在未来 LiveBroker ADR 中单独借用。
  • 迁移：阶段 2 引入 domain/ 契约；阶段 3 引入 AccountLedger；阶段 4 执行现实性； 阶段 5 LiveBroker。

Alternatives

  • vn.py：国内实盘生态更好，但 EventEngine/OmsEngine/App 架构较旧，回测/实盘一致性 弱，容易重新引入全局状态。若未来券商接入成为主要约束，另写 ADR 引入薄 LiveBroker 适配器，而不是改整体架构。
  • Backtrader：简单，但部分成交、订单类型、T+1、实盘支持不足。
  • Zipline/Qlib：研究/回测强，但不满足未来实盘和可视化同管线要求。

Verification

  • docs/architecture.md#10-nautilustrader-概念映射 的映射表完整。
  • 阶段 2–5 的契约和测试不暴露 Nautilus 类型。
  • 不在 pyproject.toml 增加 Nautilus 运行时依赖。
  • 新依赖/参考框架变化必须新 ADR。

0002: 单一所有者与单向依赖

  • Status: Accepted
  • Date: 2026-11-04
  • Owner: architecture
  • Supersedes: none
  • Superseded by: none

Context

当前现金/持仓存在多份表示：engine.positions、strategy.positions（共享引用）、 PositionManager.positions（副本）、RiskManager 的资本派生值。strategy 还 lazy import datafeeder。这导致对账困难、状态分叉，且无法安全添加实盘/可视化。

Decision

  1. 每个可变状态只有一个 owner/writer。完整表见 ../design_spec.md#4-单一真相源。
  2. 单向依赖：编排/适配器 → domain/，不能反向或横向。矩阵见 ../architecture.md#7-依赖矩阵。
  3. 现金/持仓/成本/可卖数量/已实现 PnL 的唯一 writer 是 execution/AccountLedger；其他层只读 AccountSnapshot。
  4. 策略只读 StrategyContext，只发 Intent；不得持有账本。
  5. portfolio/ 只做 sizing，risk/ 只做决策，不存现金/持仓。
  6. 派生视图/报表可以多份，但必须只读、可重建；适配器多实现同一端口不算重复。

Consequences

  • 正面：对账简单；策略可替换；回测/实盘/可视化共享状态模型。
  • 负面：迁移期需要兼容层；旧代码的多份状态要逐步删除。
  • 迁移：阶段 2 引入 domain/；阶段 3 合并到 AccountLedger；阶段 6 删除 strategy.positions/strategy.cash/PM/RM 资本副本。

Alternatives

  • 保持现状：继续在 engine 上叠加，状态会继续分叉，实盘对账不可靠。
  • 只加锁/同步：治标不治本，仍有多个 writer。
  • 微服务/独立账户服务：单人系统过度设计，增加运维成本。

Verification

  • 新增 import contract 检查（阶段 1）。
  • 阶段 3 黄金回测：账本外无现金/持仓写入。
  • 代码审查 checklist：每个可变状态是否只有一个 writer。
  • 文档所有权表与包图一致。

0003: 回测/paper/live/可视化共用一条管线

  • Status: Accepted
  • Date: 2026-11-04
  • Owner: architecture
  • Supersedes: none
  • Superseded by: none

Context

当前 BacktestEngine 和 PaperTradingEngine 各自复制了一套流程；未来实盘如果另写 一套，会形成无法回测的实盘分支。可视化也容易直接读 engine 内部状态。

Decision

所有模式共用同一条事件序列：

DataPortal + Clock
  -> Strategy.on_bar(ctx) -> [Intent]
  -> RiskPolicy.evaluate -> SizingPolicy
  -> OrderManager -> Broker(Sim/Live) -> [Fill]
  -> AccountLedger.apply(fill) -> AccountSnapshot
  -> Strategy.on_fill + observability + visualization
  • backtest = 历史 DataPortal + SimClock + SimulatedBroker。
  • paper = 实时 DataPortal + RealClock + SimulatedBroker。
  • live = 实时 DataPortal + RealClock + LiveBroker。
  • visualization = 订阅只读事件/快照，不写回。

只替换适配器；Strategy、SizingPolicy、RiskPolicy、AccountLedger 必须复用。 不引入 message bus/actor/async 运行时；同步主循环足够。

Consequences

  • 正面：策略/风控/账本只写一次；backtest/paper/live 行为一致；可视化天然只读。
  • 负面：需要 BrokerPort/Clock/DataPortal 抽象；迁移期有双路径。
  • 迁移：阶段 3 建账本/模拟 broker；阶段 4 执行现实性；阶段 5 paper/live/可视化。

Alternatives

  • backtest/live 两套代码：最常见但最危险；策略行为会分叉。
  • 直接采用 Nautilus/LEAN 运行时：过重，且 A 股/港股规则仍需自建。
  • 事件总线/微服务：单人系统过度设计。

Verification

  • 同一策略/配置在 SimulatedBroker 与 paper 适配器上产生一致的订单/成交序列（parity test）。
  • live 路径不得 import 策略私有实现；只通过契约。
  • visualization 不能写 AccountLedger/Strategy 状态。
  • paper trading 3–6 个月通过后才能实盘。

0004: 执行现实性规则

  • Status: Accepted
  • Date: 2026-11-04
  • Owner: architecture
  • Supersedes: none
  • Superseded by: none

Context

当前回测同 bar 收盘成交、只能全平、不看盘中 high/low、无 T+1/涨跌停/部分成交。这样 测出的止损/止盈/分批结果不可信，尤其对 A 股。

Decision

执行层必须实现：

  1. D+1：D 日收盘决策，最早 D+1 开盘成交；禁止同 bar 收盘成交。
  2. 订单类型：MARKET/LIMIT/STOP/STOP_LIMIT；执行层不认识 ATR/策略概念。
  3. 盘中触发：卖出止损 low <= stop → min(open, stop)；止盈 high >= target → max(open, target)；跳空按 open。同日双触发默认止损优先。
  4. T+1：A 股买入次日才可卖；ledger 维护 sellable_qty。港股 T+0。
  5. 涨跌停/停牌：方向不利封板不成交；顺延/过期显式；连续未成交标 forced_exit。
  6. lot/tick：A 股 100 股整手；港股 board lot；价格按 tick。
  7. 逐笔费用：每笔 fill 走 cost.TransactionCost；最低佣金、卖出印花税、港股印花税 取整；费用明细写入 Fill。
  8. 部分成交/部分退出：Intent.qty/ExitPlan.partials；R 分母不变；每笔费用独立。
  9. 确定性：回测无 datetime.now()、未播种随机、事件循环内网络。
  10. 复权/PIT：执行用可交易 raw price；分析用 adjusted；复权因子必须 PIT。

Consequences

  • 正面：止损/止盈/分批结果可信；回测更接近实盘；A 股规则显式。
  • 负面：实现复杂度上升；需要更多不变量测试；旧回测结论需重跑。
  • 迁移：阶段 4；依赖阶段 3 的单账本。

Alternatives

  • 继续收盘全平：无法测分批/盘中止损，结论不可用。
  • 只做日线近似：可以过渡，但必须标注，不能作为主结论。
  • 直接接实盘验证：成本/风险太高，且无法复现。

Verification

不变量测试：

  • 滑点对称，amount == shares × price；
  • 信号 D → 成交 D+1；
  • 部分卖出后现金/成本/R 守恒；
  • A 股 T+1、涨跌停不可成交；
  • 跳空按 open；
  • 棘轮只上移；
  • 每笔费用可加总。
